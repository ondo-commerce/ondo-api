# 주문 접수 재시도 — 측정 기록

도매가 멈췄을 때 밀린 주문을 서버가 대신 넣는다(MUL-137). 여기 있는 건 **재시도 간격
정책을 어떻게 골랐는가**에 대한 근거다.

```
load/order-retry/
  README.md                       이 문서
  results/policy-comparison.md    정책 비교 표 (하네스가 덮어쓴다)
```

하네스는 코드 쪽에 있다 — `retail-api/src/test/java/com/ondo/retail/order/RetryPolicyMeasurement.java`

---

## 문제 — 재시도는 장애를 더 키울 수 있다

도매가 죽으면 밀린 주문이 **한꺼번에** 실패한다. 그대로 두면 같은 무리가 같은 주기로
도매를 계속 두드리고, 막 일어난 도매가 다시 쓰러진다.

두 가지를 같이 봐야 한다.

- **총 호출 수** — 아픈 도매를 몇 번이나 두드렸나
- **몰림** — 한 순간에 몇 개가 동시에 덮쳤나

---

## 잰 것

| | |
|---|---|
| 조건 | 밀린 주문 200 건 · 도매 장애 10 초 · 간격 200ms 부터 두 배(상한 3.2초) |
| 정책 | 고정 · 지수 · 지수 + 지터(±20%) |
| 반복 | 정책마다 3 회, 항목별 중앙값 |

결과는 [`results/policy-comparison.md`](results/policy-comparison.md).

| 정책 | 도매 호출 | 최대 몰림 | 복구 시간 |
|---|---:|---:|---:|
| 고정 | 9,193 | 124 | 236 ms |
| 지수 | **1,401** | 141 | 2,836 ms |
| **지수 + 지터** | 1,374 | **25** | 3,731 ms |

둘이 서로 다른 문제를 푼다.

**지수는 총량을 줄인다** — 9,193 → 1,401. 아픈 도매를 두드리는 횟수가 85% 줄었다.

**지수는 몰림을 못 줄인다** — 124 대 141 로 고정과 다를 게 없다. 밀린 200 건 대부분이 여전히
한 칸에 들어간다. 간격은 벌어지지만 **같은 순간에 실패한 건들이 같은 곡선을 타서 같은 순간에
깨어나기** 때문이다. 파도가 뜸해질 뿐 크기는 그대로다.

**몰림을 푸는 건 지터뿐이다** — 141 → 25. 호출 총량은 지수와 같은데(1,401 대 1,374) 한 순간에
덮치는 양만 82% 줄었다.

### 대가 — 복구가 1초 늦다

지터는 각 건의 대기를 흩뜨리므로 **뒤로 처지는 건**이 생긴다. 복구 시간은 마지막 한 건까지라
2.8초에서 3.7초가 된다.

그런데 표를 나란히 놓으면 이 대가가 왜 싼지 보인다.

```
고정   복구 236ms  ⚡ 제일 빠르다   몰림 124  💥 제일 세게 때린다
지터   복구 3.7초                  몰림 25
```

**고정이 지터보다 15배 빠르다.** 도매가 살아나면 200ms 안에 다 들어간다. 그런데 그 순간
124 건이 동시에 도매를 때린다. 막 일어난 도매가 그걸 맞으면 **다시 쓰러진다.**

```
도매 살아남 → 124 건 동시 투하 → 도매 또 죽음 → 다시 밀림 → 또 124 건 …
```

그러면 복구가 아예 안 된다. **"236ms 만에 복구" 는 도매가 그걸 버텨줄 때만 의미가 있는
숫자다.** 25 건씩 나눠 들어가면 도매가 버티고, 3.7초 걸려도 진짜로 끝난다.

> 문이 열리자마자 200 명이 한꺼번에 밀고 들어가면 문이 부서진다.
> 줄 서서 들어가면 3초 더 걸려도 들어가진다.

그리고 소매처 입장에서 **도매가 이미 20초 죽어 있었다.** 거기에 1초가 더 붙는 걸 알아차릴
사람이 없고, 기한은 30분이다. 체감이 안 되는 1초를 주고 도매가 다시 쓰러질 위험을 샀다.

## 측정을 네 번 고쳤다

측정이 주장과 어긋나면 주장이 아니라 측정을 먼저 의심해야 한다. 네 번 다 측정이 틀렸다.

**① 칸을 간격보다 크게 잡았다** — 몰림을 100ms 칸으로 셌는데 재시도 간격이 20~320ms 라
여러 세대가 한 칸에 뭉쳤다. 정책이 흩뜨린 것을 측정이 다시 모은 셈이다. 지터가 몰림을
**더** 만든 것처럼 나왔다. 칸을 기준 간격과 같게 낮췄다.

**② 호출 시각으로 쟀다** — 워커가 한 바퀴에 밀린 것을 몰아 처리하므로, 실제 호출 시각은
정책이 아니라 워커 루프 속도를 따라간다. 셋이 똑같이 나왔다. **예약된 시각**(`next_attempt_at`)
으로 바꿨다 — 정책이 정하는 건 그 값이고, 도매가 맞는 파도의 크기도 거기서 결정된다.

**③ 간격이 워커 한 바퀴보다 짧았다** — 20ms 간격에 200 건을 처리하는 시간이 그만큼이라,
지수도 처리 시간 때문에 저절로 흩어져 지터와 구분되지 않았다(24 대 23). 간격을 200ms 부터로
키우자 87 대 24 로 갈렸다. **측정 장치가 재려는 값보다 굵으면 아무것도 안 보인다.**

**④ 한 번만 쟀다** — 같은 정책이 실행마다 88 과 115 로 나왔다. 도매가 살아나는 순간이 워커의
한 바퀴 중 어디에 떨어지느냐에 따라 달라진다. 정책마다 3 회 돌려 항목별 중앙값을 쓴다
(대시보드 집계 측정과 같은 방식).

이걸 고치고 나서야 **지수가 몰림을 못 줄인다**는 게 드러났다. 한 번만 쟀을 때는 87 로 나와
줄어든 것처럼 보였고, 나는 문서를 그 숫자에 맞춰 고쳤었다. 중앙값으로 보니 고정 124 · 지수 141 —
다를 게 없다. **처음 세운 가설이 맞았고, 그걸 뒤집은 건 흔들리는 측정이었다.**

또 하나, 처음엔 재시도 횟수 상한이 12 라 **고정 정책만 장애 중에 횟수를 다 써버려**
전부 포기했다. 상한에 걸린 것과 간격 때문에 덜 두드린 것이 섞이면 무엇 때문에 호출이
줄었는지 알 수 없다. 상한을 사실상 없앴다.

## 재현

측정은 평소에 안 돈다. 수십 초가 걸리고 결과를 파일로 내보내서 일반 테스트와 섞이면 안 된다.

```bash
docker compose -f db/compose.yml up -d        # 소매 DB (5433)
cd retail-api
./gradlew test --tests '*RetryPolicyMeasurement*' -Dmeasure=true
```

결과가 `load/order-retry/results/policy-comparison.md` 에 덮어써진다.

### 왜 워커만 재나

HTTP 처리량은 이 사례의 관심사가 아니다. **재시도 기계가 도매를 몇 번 두드리는지**를
봐야 하므로 대기함에 줄을 직접 넣고 워커를 돌린다. 도매는 가짜로 세우고 "죽었다 /
살아났다" 를 스위치로 만든다.

### 왜 간격을 짧게 잡았나

운영값(1초부터 두 배씩, 상한 60초)으로 재면 한 정책에 몇 분이 걸린다. 비율이 같으면
몰림의 모양도 같다 — **절대 시간이 아니라 정책 사이의 차이**를 보는 측정이다.

## 장애 주입 스위치

HTTP 경로로 직접 흔들어 볼 때 쓴다. 로컬 전용이다.

```bash
curl -X POST 'localhost:8080/api/retail/dev/fault?failRate=1'    # 도매가 죽었다
curl -X POST 'localhost:8080/api/retail/dev/fault?failRate=0.5'  # 불안정하다
curl -X POST 'localhost:8080/api/retail/dev/fault?failRate=0'    # 살아났다
curl 'localhost:8080/api/retail/dev/fault'                       # 지금 비율과 막은 횟수
```

**서버를 내리지 않고 주입하는 이유** — 내리면 0% 와 100% 만 만들 수 있다. 50% 는 도매가
살아는 있는데 불안정한 상태이고 실제 장애는 그 모양인 경우가 많다. 숫자로 주면 같은
조건을 몇 번이고 다시 만들 수 있다.

**배포에는 이 빈이 아예 안 생긴다** — `@Profile("!deploy")` 라 dev·prod 어느 쪽에도
올라가지 않는다.
